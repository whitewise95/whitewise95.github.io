01 / PERFORMANCE

걸음수 랭킹 재집계 시간을 줄였습니다.

걷기 챌린지 참가자가 늘면서 랭킹 재집계가 약 10분까지 길어졌습니다. 원천 걸음 데이터를 반복 조회하던 방식을 바꿔 집계에 필요한 데이터를 먼저 준비했습니다.

분 단위 선집계MongoDB비동기 처리

문제

재집계할 때마다 원천 걸음 데이터를 다시 읽고 계산해 참여자가 늘수록 처리 시간이 길어졌습니다. 중복 캐싱과 집계 작업도 남아 있었습니다.

구현

  • 걸음수를 분 단위로 선집계하고 랭킹 재집계에는 이 결과를 사용했습니다.
  • 재집계를 비동기로 처리하고 불필요한 중복 캐싱·집계 작업을 제거했습니다.
  • MongoDB 랭킹 데이터에 임시 데이터 TTL을 적용하고, 종료된 챌린지와 프라이빗 게임의 조회 구조를 정리했습니다.

결과

약 10분 → 1분 이하

걸음수 랭킹 재집계 시간을 단축했습니다.

02 / CONCURRENCY

한정 수량 리워드의 중복 지급을 제어했습니다.

챌린지 결과에 따라 지급하는 리워드와 티켓은 여러 요청이 같은 수량을 동시에 변경할 수 있습니다. 지급 상태를 확인하고 갱신하는 구간을 보호했습니다.

Spring BootPostgreSQLRedis

문제

한정 수량의 리워드와 티켓을 동시에 요청하면 재고 확인과 지급 처리 사이에 다른 요청이 끼어들 수 있었습니다.

구현

  • DB 비관적 락으로 지급 상태를 확인하고 변경하는 구간을 보호했습니다.
  • Redis 기반 락을 적용해 동시 요청에 따른 중복 지급을 제어했습니다.

결과

동시 요청에서 한정 수량 리워드와 티켓의 중복 지급을 제어하는 처리 구조를 마련했습니다.

03 / VERIFICATION

광고 보상을 서버에서 검증했습니다.

광고 시청 결과를 클라이언트의 요청만으로 지급하지 않도록 AdMob SSV 콜백을 검증하고, 보상 처리에 필요한 사용자와 요청 정보를 확인했습니다.

AdMob SSVECDSARedis Lua Script

문제

외부 광고 콜백의 진위와 요청 대상 사용자를 확인하고, 반복 요청이나 동시 요청이 보상 지급에 영향을 주지 않도록 해야 했습니다.

구현

  • ECDSA 서명을 검증하고 Google 공개키를 Redis에 캐싱했으며 keyId에 따라 갱신했습니다.
  • 리워드 요청과 사용자 계정의 일치 여부를 확인했습니다.
  • DB 비관적 락으로 동시 요청의 중복 처리를 제어하고 Redis Lua Script로 요청을 제한했습니다.
  • SSV 오류와 보상 처리 이력을 기록했습니다.

결과

검증부터 지급까지 서버에서 판단하고, 중복 요청과 실패 내역을 추적할 수 있는 흐름을 구축했습니다.

04 / OPERATIONS

반복되는 푸시 발송 실패를 줄였습니다.

더 이상 사용할 수 없는 디바이스 토큰이 남아 있으면 같은 발송 실패가 반복됩니다. 실패 원인과 토큰 정리 시점을 분리해 발송 흐름을 정리했습니다.

FCM비동기 트랜잭션디바이스 토큰

문제

유효하지 않은 디바이스 토큰에 다시 푸시를 보내 동일한 실패가 반복됐습니다. 토큰 정리 작업이 발송 처리에 영향을 주는 것도 피해야 했습니다.

구현

  • FCM 발송 실패 원인을 분류하고 유효하지 않은 토큰을 탐지했습니다.
  • 토큰 제거를 비동기 트랜잭션으로 분리하고 제거 이력을 사용자 이벤트로 남겼습니다.

결과

사용할 수 없는 토큰을 정리해 같은 실패가 반복되는 경로를 줄이고, 발송과 정리 작업을 분리했습니다.
